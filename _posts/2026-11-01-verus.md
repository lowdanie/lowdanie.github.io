# Introduction

[Verus](https://github.com/verus-lang/verus)
is a framework for verifying properties of Rust code.
An interesting feature of Verus is that we can use it to define an abstract mathematical model 
of a system’s behavior,
then prove that a concrete Rust implementation behaves according to that model.
In this post, we’ll model a queue using a mathematical sequence, implement it with a ring buffer, 
and prove that the implementation satisfies the specification.

# Queues

A [queue](https://en.wikipedia.org/wiki/Queue_(abstract_data_type)) is a data structure
that stores a sequence of values in first-in, first-out (FIFO) order. Values are
_pushed_ to the back of the queue and _popped_ from the front.

For example:

```
                    front → back
Start empty:        []
push(1):            [1]
push(2):            [1, 2]
push(3):            [1, 2, 3]
pop() → returns 1:  [2, 3]
push(4):            [2, 3, 4]
pop() → returns 2:  [3, 4]
```

# Ring Buffers

In this section we'll implement a queue in Rust. Specifically, we will implement
a _bounded queue_ which has a maximum capacity and rejects `push` operations when
full.

First we must  decide which type of container to use to store
the sequence of values. A natural choice is to use a vector, `Vec<T>`.
However, removing the first element from a vector requires shifting all the
remaining elements one position to the left.
One way to avoid this shift is to use a [ring buffer](https://en.wikipedia.org/wiki/Circular_buffer)

A ring buffer is an array with fixed size `N`, an index `head` that points to the front of
the queue and an integer `len` that records the queue's length. The benefit of this is
that we can pop a value in constant time by incrementing the `head`.

Here is an example with `N=3`:

```
Capacity: 3          Array slots     head  len   Queue (front → back)
Start empty:         [_, _, _]         0    0    []
push(1):             [1, _, _]         0    1    [1]
push(2):             [1, 2, _]         0    2    [1, 2]
push(3):             [1, 2, 3]         0    3    [1, 2, 3]
pop() → returns 1:   [1, 2, 3]         1    2    [2, 3]
push(4):             [4, 2, 3]         1    3    [2, 3, 4]
pop() → returns 2:   [4, 2, 3]         2    2    [3, 4]
```

Note that `push(4)` wraps around and inserts `4` into the `0`-th index of the array.
In general, the index of the `i`-th element of the queue in the buffer satisfies:

```
queue[i] = buffer[(head + i) % N]
```

The modular wrap wrap around behavior is why it is called a _ring_ buffer.

Here is an implementation in Rust:

```rust
pub struct RingBuffer<const N: usize> {
    data: [u64; N],
    head: usize,
    len: usize,
}

impl<const N: usize> RingBuffer<N> {
    pub fn new() -> Self {
        assert!(N > 0 && N <= usize::MAX / 2);
        Self {
            data: [0; N],
            head: 0,
            len: 0,
        }
    }

    pub fn len(&self) -> usize {
        self.len
    }

    pub fn is_empty(&self) -> bool {
        self.len() == 0
    }

    pub fn is_full(&self) -> bool {
        self.len() == N
    }

    pub fn try_push(&mut self, value: u64) -> Result<(), u64> {
        if self.is_full() {
            return Err(value);
        }

        let tail = (self.head + self.len) % N;
        self.data[tail] = value;
        self.len += 1;

        Ok(())
    }

    pub fn pop(&mut self) -> Option<u64> {
        if self.is_empty() {
            return None;
        }

        let value = self.data[self.head];
        self.head = (self.head + 1) % N;
        self.len -= 1;

        Some(value)
    }
}
```

This implementation is straightforward but there are a few subtleties. First, we
require that

```
N <= usize::MAX / 2
```

so that the sum `self.head + self.len` does not overflow. Furthermore, this queue
has a maximum capacity of `N` and so it is important
to check if the buffer is full before pushing in order to avoid overwriting data.

In the next section we will use Verus to formally specify our intuitive definition
of a queue from the [previous section](#queues) and prove that our `RingBuffer`
satisfies it.

# A Ring Buffer Specification

## View

We will model a queue using Verus's model of a sequence, `Seq<u64>`.

The first step is to establish a correspondence between our concrete `RingBuffer` and
a `Seq` based model. In Verus, the mapping of a concrete type to a model is called
a _view_ and it is defined via the `View` trait:

```rust
verus! {
impl<const N: usize> View for RingBuffer<N> {
    type V = Seq<u64>;

    closed spec fn view(&self) -> Seq<u64> {
        Seq::new(self.len as nat, 
            |i: int| { self.data@[((self.head as int + i) % (N as int))] })
    }
}
}
```

Let's unpack this. First, the `verus!` macro lets us write Rust code together 
with _ghost code_: code used for verification that is erased before execution.

The `View` trait consists of a model type `V` and a mapping `view` from an instance
of a concrete type to an instance of `V`. The `view` method is declared as a `spec`
function which means that it is ghost code used only for definition mathematical specifications.

For a value `x` whose type implements `View`, Verus provides the shorthand `x@` for `x.view()`.

In this case, the model type is `Seq<u64>`. Our `view` function maps a `RingBuffer` `self`
to a sequence containing `self.len` values starting from index `self.head` and
wrapping around by the modular arithmetic rule from section
[Ring Buffers](#ring-buffers).

Note that the array type `[u64; N]` itself implements the
`View` trait and maps an array `x: [u64; N]` to a model sequence `seq: Seq<u64>`
of length `N` satisfying:

```rust
seq[i] == x[i]
```

So the expression `self.data@` is the model sequence of length `N`
corresponding to the array `self.data`.
Similarly, if `rb: RingBuffer<N>` is a ring buffer then `rb@` is its
associated model sequence of length `rb.len`. 

## Specification

In the previous section we implemented a `View` mapping a `RingBuffer` to our mathematical
model of a queue. We can now use this mapping to define a specification for
`RingBuffer` which states that every concrete operation (e.g 'pop') is equivalent to
the corresponding operation on the abstract model.

We'll start by defining an invariant which specifies what it means for a ring buffer to
be well formed:

```rust
impl<const N: usize> RingBuffer<N> {
    pub closed spec fn inv(&self) -> bool {
        &&& 0 < N <= usize::MAX / 2
        &&& self.head < N
        &&& self.len <= N
    }
}
```

We can now define specifications for the `RingBuffer` operations. For example:

```rust
impl<const N: usize> RingBuffer<N> {
    pub fn len(&self) -> (length: usize)
        requires
            self.inv(),
        ensures
            length == self@.len(),
            length <= N,
    {
        self.len
    }
}
```

Note that the expression `-> (length: usize)` names the output of `len()` with `length`.

The `requires` clause specifies preconditions. In this case, the precondition on
`len` is simply that the ring buffer is well formed.

The `ensures` clause specifies postconditions. In this case, the `length == self@.len()`
condition says that the output `length` should be equal to the length of the 
model queue `self@.len()`.

The specifications for the rest of the operations are specified similarly:

```rust
impl<const N: usize> RingBuffer<N> {
    pub closed spec fn inv(&self) -> bool {
        &&& 0 < N <= usize::MAX / 2
        &&& self.head < N
        &&& self.len <= N
    }

    pub fn new() -> (buffer: Self)
        requires
            0 < N <= usize::MAX / 2,
        ensures
            buffer.inv(),
            buffer@ == Seq::<u64>::empty(),
    {
        ...
    }

    pub fn len(&self) -> (length: usize)
        requires
            self.inv(),
        ensures
            length == self@.len(),
            length <= N,
    {
        ...
    }

    pub fn is_empty(&self) -> (empty: bool)
        requires
            self.inv(),
        ensures
            empty == (self@.len() == 0),
    {
        ...
    }

    pub fn is_full(&self) -> (full: bool)
        requires
            self.inv(),
        ensures
            full == (self@.len() == N),
    {
        ...
    }

    pub fn try_push(&mut self, value: u64) -> (result: Result<(), u64>)
        requires
            old(self).inv(),
        ensures
            final(self).inv(),
            match result {
                Ok(()) => old(self)@.len() < N
                    && final(self)@ == old(self)@.push(value),
                Err(rejected) => old(self)@.len() == N
                    && rejected == value
                    && *final(self) == *old(self),
            },
    {
        ...
    }

    pub fn pop(&mut self) -> (result: Option<u64>)
        requires
            old(self).inv(),
        ensures
            final(self).inv(),
            match result {
                Some(value) => old(self)@.len() > 0
                    && value == old(self)@[0]
                    && final(self)@ == old(self)@.subrange(1, old(self)@.len() as int),
                None => old(self)@.len() == 0
                    && *final(self) == *old(self),
            },
    {
        ...
    }
}
```
